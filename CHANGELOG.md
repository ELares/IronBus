# Changelog

All notable changes to IronBus are documented here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project aims
to follow Semantic Versioning once it reaches a tagged release.

## [Unreleased]

### Security
- Pinned every GitHub Actions `uses:` in the CI and nightly workflows to a full commit SHA, with the human-readable tag kept as a trailing comment (#142). A mutable tag like `@v4` lets a compromised or retagged action run with the workflow's permissions; a SHA is immutable. `dtolnay/rust-toolchain` is pinned to a single SHA and the MSRV job passes `toolchain: "1.78.0"` explicitly (the bare `@stable` uses keep the action's `stable` default), so the toolchain selection no longer rides on a mutable ref.

### Changed
- Replaced the overloaded generic `Ok` response frame with distinct, self-describing response frames per verb (#179): `PubAck` (tag 14, body: the durable offset as an 8-byte LE u64), `AckStatus` (tag 15, body: a one-byte status, 0 = fenced / 1 = committed-requeued-extended / 2 = progress cap reached), and `FlowEnd` (tag 16, body: the delivered count as a 4-byte LE u32). Previously a single `Ok` carried three incompatible body shapes disambiguated only by the client remembering its last request, which was undocumented at the frame level and foreclosed request pipelining. The frame type now disambiguates the reply, so a pub offset can no longer masquerade as a one-byte committed ack. `Err` stays distinct; `Ok` is retained as a reserved body-less success and the new tags are pinned by the frozen-tag test (refs #11, #178).
- Recovery now scans each segment with a streaming reader that reads one record at a time, instead of buffering the whole record region and materializing every record's payload (#156). On a full 64 MiB segment the old path allocated the entire region plus an owned copy of every record (~2x the segment); recovery only needs each record's sequence, the valid record count, and the torn-tail boundary, so the new `SegmentReader::scan_recovery` validates each frame (header and body CRC, sequence continuity) and drops the bytes, bounding peak memory to the largest single record. The buffered `SegmentReader::scan` is retained for the delivery read path. Behavior is unchanged: a new `codec::decoded_len` reads a frame's length from its header, and a test pins that `scan_recovery` agrees with `scan` on count, last sequence, `valid_end`, clean, and footer across clean, sealed, empty, torn, and corrupt segments; the crash-recovery and determinism sweeps pass at 20000 cases (refs #115, #21).

### Fixed
- The `ironbus_recovery_loss_bytes` metric's `# TYPE` line no longer carries leading whitespace (a source-indentation artifact), so a strict Prometheus parser recognizes the type declaration; a test now pins the clean `# TYPE` lines (#16).
- `InMemoryFile` modeled `fdatasync` (`sync_data`) and `fsync` (`sync_all`) identically, treating a `set_len` truncation as durable after either (#158). A real `fdatasync` flushes data but need not persist a length-shrink (metadata), so the simulation now reverts a truncation that was only `sync_data`'d on a power loss and persists it only after `sync_all`, while in-place edits and data growth stay durable under `fdatasync`. This pins the conservative real-disk contract that `Log::recover` already follows (truncate a torn tail, then `sync_all`); a regression that truncated with only `sync_data` would now fail the crash-recovery sweep. Includes two model tests and updates the recovery-idempotence gate's torn-tail setup to make the truncation durable via `sync_all` (refs #6, #21).
- The `dead_letter_iff_a_finite_cap_is_exceeded` delivery proptest no longer relies on a `prop_assume!` that rejected ~2.5% of inputs: under a deep (nightly) sweep that exhausted proptest's global-reject budget and aborted the test. The strategy now generates only valid configs (max == 0 forces the unlimited opt-in), so it rejects nothing and is robust at any case count (refs #21).

### Added
- The golden-path acceptance test now covers #133 step 2, the health probes coming up, end to end over the real `ironbus` binary (refs #133, #16): it boots the broker with `--health-addr 127.0.0.1:0`, asserts the bound health address is loopback only, then asserts `/healthz` is `200 OK` with the exact body `ok` and `/readyz` is `200 OK` with the exact body `ready`, and that an unknown path (`/nope`) is a real `404 Not Found` with the body `unknown endpoint` (so the router is real and the healthy assertions are non-vacuous, not a blanket 200). It reuses the existing health-addr broker helper and the minimal HTTP getter; no code changed.
- Consumer-safe size-based RETENTION (refs #13, #80): a reaper that reclaims disk by deleting whole OLD SEALED segments once the durable log exceeds a configured byte bound, but NEVER a segment any consumer still needs. `Log::reap_to_size(max_retained_bytes, protect_below_offset)` loops from the oldest sealed segment, unlinking `segments[0]` only while the log is over the bound, more than one segment exists (the active segment is never reaped), and `segments[1].base_offset <= protect_below_offset` (so every record in it is below the protect floor and needed by no consumer). Each unlink dir-syncs the removal BEFORE the in-memory slot and the running sealed-bytes total change, so a crash leaves a shorter contiguous chain recovery already accepts and memory never disagrees with disk; the byte accounting decrements by `valid_end - SEGMENT_HEADER_LEN` (the exact per-segment term the sealed total accumulated). `EngineConfig.max_retained_bytes` (`0` = unlimited, the default, so existing behavior is unchanged) drives it: after a successful produce the engine reaps against the MINIMUM committed offset across all groups, so the slowest group's records are never reaped, counting reclaimed segments in `segments_reaped`, rendered on `/metrics` as `ironbus_segments_reaped_total`. A `serve --max-retained-bytes <bytes>` flag exposes it. This is the drain side of the overflow policy that complements the byte-cap shed (#259): the cap sheds new produces when full, retention frees space as consumers drain. A reap IO error propagates (state stays consistent with disk, never swallowed). Tested at every layer: storage (reaps to under the bound, never the active segment, never above the protect floor, a reopen recovers the non-zero-start chain, byte accounting matches a fresh reopen, crash-safety), engine (reclaim as the log grows, a slow group blocks reaping then unblocks on catch-up, default-off reaps nothing), and `/metrics` (renders and increments). Time/count retention (#80), compaction (#83), the disk-full drop-oldest policy (#82), and the below-earliest truncation signal (#84) remain follow-ups.
- A `serve --max-total-bytes <bytes>` flag exposing the durable-log byte cap on the CLI, and a golden-path test completing #133 step 5 (overload spill then shed) (refs #133, #10). The flag threads through `LogConfig::with_max_total_bytes` so both the segment and total caps are honored; `0` (the default) means unlimited, so an existing `serve` without it is unchanged. The new test drives the real binary with a small cap, pubs a fixed batch, and asserts spill-then-shed non-vacuously: at least one pub spills and at least one sheds, the client shed count equals `/metrics ironbus_produce_rejected_total` exactly, a further pub is promptly shed again (the broker stays live, never a hang or silent drop), and the accepted prefix is durably consumable in order.
- The drop-new shed of the spill-then-shed overflow policy: a configurable per-instance durable-log byte cap (`LogConfig::max_total_bytes`, `0` = unlimited, the default, so existing behavior is unchanged) (refs #10, #13, unblocks golden-path #133 step 5). When the log is at or over the cap, a produce is REJECTED before any write: nothing is appended, no offset or sequence advances, and the producer is told promptly with the new non-fatal `StorageError::AtCapacity` (never a silent drop, never an indefinite hang). The cap counts durable RECORD bytes (the quantity recovery sums as `durable_bytes`), tracked O(1) via a running sealed-bytes total so an append never rescans every segment; the check is at-or-over like `max_segment_bytes` (the log overshoots by at most the last record) and a record on an empty log is always written. The shed is distinct from the fatal `WriterFrozen` freeze: `AtCapacity` is non-fatal, the writer stays live, so a later produce succeeds once retention (#13) frees space. `Engine::produce` increments a new `produce_rejected` counter (a rejected produce never counts as produced), exposed on `/metrics` as `ironbus_produce_rejected_total`; the session replies a distinct, stable `at capacity` Err frame (every other non-fatal error keeps `produce failed`) and keeps the connection open, so a client surfaces the shed via `ClientError::Server` and can keep going. Tested at every layer: storage (rejection writes nothing and is absent after reopen, non-fatal, byte accounting across a roll, oversized first record written, `max_total_bytes = 0` unlimited), engine (counter increments, produced/flushed unchanged), `/metrics` rendering and increment, and a session wire test (the `at capacity` frame and the connection staying open).
- The golden-path acceptance test now covers #133 steps 6 and 7, power-cut recovery and the loss report, end to end over the real `ironbus` binary (refs #133, #7, #8, #16): it produces four durable records, stops the broker, and appends a torn tail (bytes that cannot start a valid record) to the active segment, modeling a power cut that left a partial record. With the broker stopped, `dump` shows exactly the four durable records and a torn-tail loss note of the expected byte count, never reading past the durable head. On restart, recovery truncates the torn tail and exposes the dropped byte count on `/metrics` as `ironbus_recovery_truncated_bytes`, which the test asserts equals the offline `dump` loss (the online counter and the offline reader agree), the durable prefix is fully consumable, and the log continues cleanly from the truncated head. A new health-addr broker helper and a minimal HTTP `/metrics` reader support it; the assertions are exact (the byte counts must match), so the test cannot pass vacuously. Only the overload spill and the installer steps of #133 remain.
- Four cargo-fuzz targets for the untrusted wire message-body decoders (refs #21, #123), closing the gap where the harness fuzzed the record, frame, cursor, and segment parsers but not the message bodies that parse raw client (and, for the client, server) input: `pub_body` (`message::decode_pub`) and `ack_body` (`message::decode_ack`) drive the broker's producer and consumer body parsers, and `deliver_body` (`message::decode_deliver`) and `dead_letter_body` (`message::decode_dead_letter`) drive the client's view of a server's frames. Each asserts that on any byte string the decoder only returns a typed `BodyError` or a valid view, never panicking or reading out of bounds. The nightly `fuzz` soak loop now exercises all eight targets under libFuzzer and AddressSanitizer; a local soak ran no crash on every new target.
- `docs/USAGE.md` now documents the shipped CLI surface that had landed since the guide was written (refs #15): consumer groups (`sub --group <name>`, broadcast vs competing, the durable per-group `cursor-<hex(name)>.ckpt`), the in-band `dead-letter offset=<n> reason=max-deliver` advisory `sub` prints when the broker parks a poison offset, the offline inspection verbs `peek` / `dump --data-dir` (their flags, the `offset= ts_ms= bytes= key_bytes= crc=ok codec=none` record line, the torn-tail loss note, and Unix-only), the cargo-fuzz harness under `fuzz/`, and the full exit-code scheme including the offline `2` (not found) and `4` (corrupt) codes. Each claim was verified against `crates/ironbus-cli/src/main.rs`; no code changed.
- A property test pinning the durable cursor checkpoint's single-byte-corruption invariant (refs #21, #60): for a short run of arbitrary writes followed by one flipped byte at an arbitrary offset anywhere in the two-slot file, `Checkpoint::open` never panics and returns either `None` or a payload byte-equal to one that was actually written, never a torn, partial, or invented value. This sweeps the corruption-tolerance decode path over the whole file (the flip lands in the payload region for some inputs and the seq/len/crc region for others), generalizing the existing fixed-case torn-slot tests so a regression that wrongly accepted a corrupt slot would fail. It runs per-PR under `cargo test`; the nightly lane sweeps deeper.
- The golden-path acceptance test now covers #133 step 9, offline inspection agreeing with recovery, end to end over the real `ironbus` binary (refs #133): it boots the broker, produces four records (asserting each `pub` returns its durable offset), cleanly stops the broker, then with the broker STOPPED runs `dump` and `peek` over the same data directory. It asserts the offline reader shows exactly the produced offsets 0..N, in order, with no phantom record past the durable high-water mark and no loss note on a clean directory; that `peek --limit` and `peek --from-offset` read a bounded subset still capped at the durable head; and that `dump --json` is valid NDJSON, one record object per line, offsets 0..N, no loss object. Records are fsynced before `pub` returns the offset, so the directory is durable after the broker exits. The assertions are on the exact set of offsets, not a loose contains, so the test cannot pass vacuously.
- A wire dead-letter advisory so a fetching consumer learns when an offset was dropped as poison (refs #63, #11): when a message exceeds `MaxDeliver` the engine parks it (committed past, never redelivered), but until now the consumer was told nothing and just silently never saw that offset. A new `DeadLetter` frame (wire tag 17, body: the dead-lettered `offset` as an 8-byte LE u64 plus a one-byte reason, 0 = max-deliver exhausted) is now emitted in-band during a Flow batch for each parked offset. `Client::fetch` returns a `Fetch { messages, dead_letters }` carrying any advisories alongside the deliveries (the credit caps the total frames a server may stream, deliveries plus advisories, so a hostile server cannot stream either unboundedly), and `ironbus sub` prints a `dead-letter offset=<n> reason=max-deliver` line. The durable DLQ topic write and idempotent reconciliation remain the larger #63 work; this is the in-band notification half. Tests: a proto codec round-trip and short/overlong rejection, the frozen-tag test pins tag 17, a client test that `fetch` surfaces an advisory from a scripted batch, and the existing end-to-end poison test now asserts the consumer is told. The `/metrics` `ironbus_dead_lettered_total` counter and `ironbus_last_dead_lettered_offset` gauge already existed; this adds the consumer-facing signal.
- The golden-path acceptance test now covers #133 step 4, consumer-group fan-out, end to end over the real `ironbus` binary (refs #9, #133): one durable log fans out to a broadcast group (its own cursor, sees every message) and a competing group (two members sharing one cursor, each message to exactly one member), and the two groups advance independently. The test produces four records, drains the broadcast group (asserts it sees all four), then drains the competing group across two members with bounded credit (asserts the members' deliveries are disjoint and together cover the batch exactly once, none dropped or doubled), then asserts a fresh fetch on each group sees nothing (independent progress over the same log). It restarts the broker and asserts both groups resume past their acks, exercising the durable per-group cursors (#60, #248) over the wire. `--checkpoint-interval 1` checkpoints each group synchronously per ack, so the restart resume races nothing; sequential `sub` calls keep the competing-member split deterministic. The remaining #133 steps (overload spill, the simulated power cut, the loss report, the installer) stay open.
- An engine-level both-slots-torn checkpoint crash gate (refs #21, #164): a test that drives a queue until BOTH slots of the two-slot cursor checkpoint (#235) hold a real, distinct snapshot, then flips a crc32c-covered payload byte in each slot and reopens the engine over the doubly-corrupt file. It asserts the engine fails SAFE: `Engine::open` never errors or panics, the unreadable cursor is discarded, and every durable record redelivers from offset zero exactly once as a fresh first delivery (at-least-once: duplicates allowed, a lost ack is not). The two-slot scheme means a single torn write can only damage one slot, so this models the worse media-rot or double-fault case the per-PR gates did not yet cover end-to-end; the `Checkpoint` unit tests already pin the byte-level behavior, this pins the engine's consumption of it. A control branch runs the identical lifecycle with an intact checkpoint and asserts it resumes at the committed head and redelivers nothing, so the test cannot pass vacuously. This closes the last block-layer item #164 left open now that the checkpoint exists.
- A cargo-fuzz harness that continuously soaks the four untrusted-byte parsers under libFuzzer and AddressSanitizer (refs #21, #123), making good the README's claim that the record and segment parsers are continuously fuzzed. A detached `fuzz/` crate (its own empty `[workspace]` table, so the stable merge-blocking workspace is never built with the nightly sanitizer toolchain) defines four targets: `record_codec` (the record-frame decoder `codec::decode` / `decoded_len`), `frame_decode` (the length-framed wire decoder `frame::decode_frame`), `cursor_snapshot` (the `AckCursor` snapshot decoder), and `segment_scan` (the recovery `SegmentReader::open` / `scan` / `scan_recovery` over arbitrary on-disk bytes, the most security-critical parser since it runs on every startup over bytes a power cut may have corrupted). Each asserts the contract the proptests assume on structured inputs: on any byte string the parser only returns a typed error or a valid view, never panicking or reading out of bounds. A new nightly `fuzz` job installs a pinned cargo-fuzz and soaks every target for three minutes under ASan; a crash fails the run and uploads the offending input so it can be minimized into a permanent regression seed. The targets and the soak job are SHA-pinned and actionlint-clean, the build outputs and discovered corpora are git-ignored, and `Cargo.lock` is committed for reproducibility. A local soak ran 6M to 21M executions per target with no crash.
- A power-cut-with-write-reordering crash gate (refs #21): a property test that punches a zeroed hole strictly inside the unsynced tail (the durable prefix left intact), modeling a power loss that persisted only part of the unsynced writes, and asserts recovery loses no acked record (I1: it recovers at least the durable prefix), is a contiguous valid run from offset 0 (I2: it truncates at the first gap and never reads past it), and every survived record's payload is intact. This is stronger than the existing all-or-nothing power-loss gate: a partial tail is truncated at the first gap, never dropping a durable record below it. It runs per-PR under cargo test; the crash-recovery doc records the newly covered class.
- Durable per-work-group cursors (refs #60, #9): a named consumer group's committed cursor (the watermark plus its acked-ahead set) now survives a restart instead of redelivering the whole log from offset 0. Each named group checkpoints to its own `cursor-<hex(name)>.ckpt` file (the group name is hex-encoded so a path-unsafe name like `team/a:1` is a safe, reversible filename), reusing the crash-safe two-slot checkpoint and the `AckCursor` snapshot codec (#235); the default group keeps `cursor.ckpt`. On open the engine discovers and resumes every `cursor-<hex>.ckpt`, clamped to the durable head, bounded by the group cap. New engine methods `checkpoint_group` / `maybe_checkpoint_group` route a connection's flush and interval checkpoint to its subscribed group (via a new `Session::subscription`), so the server persists the right group on clean disconnect and on the configured interval; an unsubscribed connection keeps the default-group behavior unchanged. Tests cover a named group resuming past its acked tail, an out-of-order acked-ahead set surviving, multiple groups resuming independently, durability on a real directory with a path-unsafe name, and that `cursor.ckpt` / segment files are never mistaken for a group checkpoint. The in-flight lease state (attempt counters, the Pending Entries List) is still reconstructed empty on restart (at-least-once safe); a per-consumer state-event log with snapshot-plus-tail replay remains the larger #60 work.
- An `ironbus_produced_bytes_total` counter on `/metrics` (refs #96, #16): the logical message bytes appended by produce (key + headers + payload, excluding the record framing), a throughput and flash-wear signal alongside the existing `ironbus_produced_total` record count. Tracked on the engine's produce path (saturating) and rendered next to the record counter; the `/metrics` test asserts the byte total.
- A per-reason recovery-loss RECORD-count series on `/metrics` (refs #96, #16, #120): `ironbus_recovery_loss_records{reason="..."}` reports how many records recovery dropped at the last startup, broken down by `ReasonCode`, the record-count complement of the existing `ironbus_recovery_loss_bytes` series, so an operator sees not just how many bytes recovery dropped but how many records, by reason. Backed by a new `LossReport::records_lost_for(reason)` (mirroring `bytes_skipped_for`). The per-reason totals sum to `total_records_lost_estimate`. This advances the #96 contract that every skip is counted, not only sized.
- A tagged-release pipeline for the static musl edge binaries (refs #17, #22): pushing a `v*` tag (or a manual `workflow_dispatch`) runs `.github/workflows/release.yml`, which cross-builds the static `ironbus` binary for all three triples (x86_64, aarch64, armv7 musl, the same setup the CI `musl build` jobs prove), asserts each is statically linked, attaches a SHA256 checksum and a `cargo-auditable` SBOM (`ironbus.sbom.json`), signs every artifact with a keyless Sigstore build-provenance attestation (no key to manage, verifiable with `gh attestation verify`), and publishes a GitHub Release. Two new merge-blocking CI jobs back it: `sbom` builds the musl binary with `cargo auditable` and verifies the embedded dependency manifest lists the workspace crates (so the release SBOM path is exercised every PR, not first at a tag), and `actionlint` lints every workflow (schema, expressions, and shellcheck on each run block), so a broken release workflow is caught on a PR rather than at an un-retryable tag. `RELEASING.md` documents the cut-a-release and verify-a-binary steps. Byte-reproducible two-runner builds remain #101.
- Per-work-group consumer metrics on `/metrics` (refs #16, #15, #9): lag broken down by cursor. Now that the broker fans out to named consumer groups, the endpoint exposes `ironbus_group_committed_offset`, `ironbus_group_consumer_lag`, and `ironbus_group_in_flight`, each labeled by `group`, for every live work-group (the default group is the empty label). The existing un-labeled gauges (the default group's committed/lag/in-flight) stay for back-compat. A new `Engine::group_consumer_stats` returns each group's committed offset and in-flight depth; the lag is derived against the durable head. Group names are escaped for the Prometheus label value (backslash, quote, newline), and the series count is bounded by the per-engine group cap (#240). Tests assert two groups at different positions report distinct lag and in-flight, and the label escaping is unit-tested. Per-member in-flight depth (for the #64 hot-spot signal) remains a follow-up.
- Consumer groups are now usable from the client and the CLI (refs #9): `Client::subscribe(group)` and `Client::unsubscribe()` join or leave a named work-group (sending the wired `Sub` / `Unsub` frames and awaiting the `Ok`), and `ironbus sub --group <name>` subscribes before fetching so an operator can run a broadcast consumer or a competing group from the single binary. An empty name keeps the default group, so existing callers are unchanged. The name's shape and the group cap (#240) are enforced by the server on the first fetch and surfaced as a `ClientError::Server`. New end-to-end tests (over a real server) prove two clients subscribed to different groups each independently receive every message (broadcast fan-out), that an invalid group name surfaces a server error on fetch, and that `ironbus sub --group` routes to the named group with an independent cursor. This completes the operator-facing path for golden-path #133 step 4; per-key `key_shared` routing (#64) and durable per-group cursors (#60) remain follow-ups.
- Consumer groups are now reachable over the wire (refs #9, golden-path #133 step 4): the reserved `Sub` / `Unsub` frames are wired, so a consumer names the work-group it joins and its `Flow` fetches and `Ack` / `Nack` / `Term` / `Progress` route to that group. A new `SubBody` proto codec carries the group name (the whole frame body; an empty name selects the default group); the session stores the active subscription and routes through the engine's `poll_in` / `ack_in` / ... (a new `Engine::poll_now_in` reads the engine clock and polls a named group). A connection that never subscribes uses the default group exactly as before, so the existing client, the golden path, and the determinism gate are unchanged. Subscribing or unsubscribing drops this connection's outstanding leases in the previous group (they redeliver there after the visibility timeout), and the name's shape and the group cap (#240) are enforced by the engine on the first fetch, surfaced as an `Err` frame. New wire tests prove two connections on different groups each independently receive every message (broadcast fan-out), that an ack commits only the subscribed group, that unsubscribe reverts to the default group, and that a non-UTF-8 subscription name is rejected. Durable per-group cursors (#60), key-shared routing (#64), and per-consumer credit (#65) remain follow-ups.
- The engine now bounds named work-group creation (refs #240, #9), a prerequisite for exposing groups on the wire: a new group is created only by `poll_in`, and only if its name is valid (1 to 128 graphic-ASCII bytes) and the per-engine cap (`MAX_GROUPS` = 1024, including the durable default) is not yet reached, else a typed `EngineError::InvalidGroupName` or `EngineError::TooManyGroups` is returned instead of allocating. This stops an unauthenticated client from exhausting memory by naming endless groups once the wire can name them. `ack_in` / `nack_in` / `progress_in` no longer create a group as a side effect: an op on an unknown group is now a fence (a consumer must poll before it can ack), so the only group-creation path is the capped one. The default group and existing groups are exempt, so the wire, the session, and the golden path are unchanged. New tests cover the cap rejecting the N+1th group, invalid names rejected before allocation, and ack/nack/progress on an unknown group fencing without creating it. Making the cap configurable via `EngineConfig` and an idle-group eviction / `Unsub` lifecycle remain #240 follow-ups.
- The engine now supports named work-groups (refs #9): each group is an independent committed cursor plus its own in-flight lease set over the single shared log, so the same log can fan out to a broadcast consumer (a group of one, seeing every message) and a competing group (shared by several members, each message to one member), every group advancing independently. New `poll_in` / `ack_in` / `nack_in` / `term_in` / `progress_in` / `committed_offset_in` take a group name; the existing `poll` / `ack` / `nack` / `term` / `progress` / `committed_offset` delegate to a durable default group (`""`), so the wire protocol, the session, and every existing test are unchanged and the golden path still passes. A `LeaseToken` is scoped to the group it was delivered from (lease generations are per-group). Only the default group is durable today (it keeps the existing `cursor.ckpt`); named groups are in-memory, so they redeliver from the start after a restart (at-least-once safe), with durable per-group state being the #60 consumer-state-store follow-up. New tests prove two named groups consume the log independently and that one group's lease never blocks another. This is the engine half of the consumer-groups keystone (golden-path #133 step 4); the wire-level Sub/group routing is the next slice.
- `ironbus peek` and `ironbus dump`, the offline inspection verbs (refs #92, #15), built on the offline reader (#90): decode and display a stopped broker's data directory with no server running. `peek --data-dir <dir> [--from-offset <n>] [--limit <n>] [--json]` shows a bounded window (default 10 records); `dump --data-dir <dir> [--limit <n>] [--json]` streams every record one per line (NDJSON with `--json`). Each record line carries offset, timestamp, byte length, key length, CRC status (always ok, since the reader only yields records that passed their checksum), and codec (always `none` until on-disk compression #12 lands). Both read only up to the durable high-water mark and MARK, never hide, any torn or corrupt tail: a trailing note (a `{"loss":...}` JSON object in `--json` mode) reports the dropped span and reason, so the holes are shown. Two new frozen exit codes join the scheme: 2 (the data directory does not exist) and 4 (the segment chain is structurally corrupt), distinct from a clean torn tail the reader reads past. Unix-only in v1, like `serve` (on-disk storage uses positioned IO the Windows path does not yet implement). Memory is bounded to one segment at a time; per-record streaming within a fixed RAM ceiling for a multi-GB segment, the `--raw` frame view, compressed-payload decoding, and `scrub` / `repair` remain #92 follow-ups.
- A read-only offline data-dir reader, `ironbus_storage::offline::OfflineReader` (refs #90, #15): decodes a stopped broker's data directory with no server running, reusing exactly the recovery decode path (`SegmentReader`) so the bytes have one authoritative interpretation. It validates the segment chain exactly as recovery does (id match, base continuity, sealed predecessors), exposes the durable high-water mark, the structured loss report, and the records one segment at a time (bounded memory). Crucially it NEVER mutates the directory: it does not truncate a torn tail or roll a segment forward, it bounds every read to the durable valid prefix (a torn or unsynced tail past the high-water mark is reported as loss but never read as a record, even when the file is physically longer), and unlike recovery it does NOT fail closed on excessive loss, since an inspector must be able to show a badly corrupted directory rather than refuse to open it. Tests cover an empty directory, a clean multi-segment round-trip, byte-for-byte agreement with online recovery on the same bytes (durable head, records, and loss report all match), and a torn tail that is bounded, reported, and left physically untouched. This is the load-bearing offline reader the `peek` / `dump` / `info` / `scrub` verbs (#92) will build on.
- The broker now persists the consumer cursor's acked-ahead set across a restart, not just the committed watermark (refs #60, #61): the engine checkpoint payload is now the full `AckCursor` snapshot (#235), so an out-of-order ack (one that leaves a lower offset unacked) survives a restart instead of redelivering. On recovery the engine decodes the snapshot and resumes with `resume_with_ahead`, clamping the watermark and dropping any acked-ahead range above the recovered durable head (at-least-once safe). A payload too short to be a snapshot is read as the legacy committed-only format (#182), so an existing checkpoint still resumes. The acked-ahead set is best-effort: if it has more disjoint runs than a 64-byte checkpoint slot holds, the watermark plus the leading runs that fit are persisted and the overflow runs simply redeliver after a crash (documented, never an ack lost below the watermark); the in-flight window bounds how large the set can grow. New engine tests cover the out-of-order-ack round-trip (only the gap redelivers), the over-cap safe degradation (the dropped runs redeliver, the kept ones do not, nothing below the watermark is lost), and the legacy committed-only checkpoint still resuming. A full per-consumer state-event log with snapshot-plus-tail replay and a Pending Entries List is the remaining #60 work.
- The on-disk snapshot codec for `AckCursor`, the byte framing the durable consumer-state store will checkpoint and recover (refs #60, #61): `encode_snapshot` appends a 1-byte version, the committed watermark, the run-length acked-ahead ranges, then a trailing crc32c; `decode_snapshot` validates length, version, and checksum, then delegates range-shape validation to `resume_with_ahead`, returning a typed `SnapshotError` (`Truncated`, `BadLength`, `UnsupportedVersion`, `BadCrc`, `Ranges`) so a torn snapshot is rejected and the caller falls back to the prior snapshot rather than restore a broken cursor. The run count is implicit in the byte length, so no separate count is stored. Tests cover the empty and multi-run round-trip, rejection of truncated, mis-sized, wrong-version, corrupt-crc, and structurally invalid snapshots, that encode appends to a non-empty buffer, and two properties at PROPTEST_CASES=20000: any cursor round-trips, and crc32c catches every single-bit flip. Still IO-free (it lives in ironbus-core like the record codec).
- `AckCursor` is now persistable, the foundation for the durable consumer-state store (refs #60, #61): `ahead_ranges()` snapshots the sparse acked-ahead set as run-length `[start, end)` ranges, and `resume_with_ahead(committed, ranges)` restores a cursor from such a snapshot, validating the shape (each range non-empty, sorted, disjoint, non-adjacent, strictly above the watermark) and rejecting a corrupt or torn snapshot with a typed `AckCursorError` so the caller can fall back to a plain `resume` (redeliver) rather than trust bad state. This lets a restart redeliver only genuinely unacked offsets instead of the acked-ahead ones too. The byte framing and CRC of the on-disk snapshot remain the storage layer's concern (#60). The versioned `--json` contract and the rest of the command tree (bench, info, consumer, peek, dump, and the offline forensics) are follow-ups under #91 and #136.
- `ironbus-client`: a synchronous client library. `Client::connect` handshakes with a broker over TCP, then `produce` (returns the assigned offset), `fetch` (returns the delivered messages, each with the offset and fencing generation), `ack` (returns whether it committed or was fenced), and `ping`. It frames the byte stream with a persistent buffer (so a read delivering several frames is never lost) and maps a server `Err` frame to a typed `ClientError`. Connect, read, and write timeouts (`ClientConfig`, finite defaults) bound every blocking call, so a silent or slow broker fails the call instead of wedging the caller forever. The client distrusts the peer's framing: it rejects an unknown frame tag (`ClientError::UnknownFrameType`), a wrong-shape `Ok` (a non-one-byte ack status or non-eight-byte produce offset, `ClientError::BadResponse`), and more deliveries than the requested credit. Tested with a real produce/fetch/ack round-trip and multi-message fetch against an in-process server, plus hostile-server cases (server `Err`, fenced ack, eight-byte-`Ok` ack confusion, over-credit fetch, unknown tag) against a scripted raw socket.
- Consumer fetch path: a client can now receive and acknowledge messages, completing the produce/consume loop over TCP. `ironbus-proto` adds a `Deliver` frame type and a `DeliverBody` codec (offset + lease generation + the message); `ironbus-server`'s session handles a `Flow` (fetch) request by polling up to the requested credit and streaming each message as a `Deliver` frame, terminated by an `Ok` carrying the delivered count, then the client acks each by its fencing token. `Engine::poll_now` polls using the engine's own clock. Tested end to end, including a full produce -> fetch -> ack round-trip over a real TCP socket.
- `ironbus-server::clock::SystemClock`: the production `Clock` over the OS clock (wall from `SystemTime`, monotonic from `Instant`), the real implementation of the seam `ironbus-core` cannot provide while staying IO-free.
- `ironbus-server::server`: a blocking, thread-per-connection TCP server. `serve` accepts connections until a shutdown flag is set, bounded by a connection cap (so a flood cannot spawn unbounded threads), and drives a `Session` per connection against the engine shared behind a `Mutex` (the single logical writer the storage layer requires; group-commit behind an append actor is a throughput follow-up). Integration-tested over real localhost sockets: a CONNECT+PUB round-trip appends to the engine and returns the assigned offset, and a malformed frame closes the connection.
- `ironbus-server::session`: the connection session that frames the wire protocol onto the engine. `Session::process` consumes the complete frames at the front of an input buffer (leaving a partial trailing frame for the next read) and writes response frames, dispatching the request/response verbs: Connect -> Info, Ping -> Pong, Pub -> Ok (with the assigned offset) into the engine, and Ack -> Ok (committing a delivered message via its fencing token). Pub/Ack before Connect, malformed bodies, and unsupported verbs reply Err without closing; a malformed frame envelope ends the session (a length-prefixed stream cannot resync). Synchronous and buffer-driven, so the async TCP server can drive it without owning IO.
- `ironbus-server::engine`: a durable consumer cursor. The engine now keeps the committed offset in a crash-safe `Checkpoint` (`cursor.ckpt` in the data directory); `checkpoint_cursor` records it, and `Engine::open` recovers it and resumes, so a restart redelivers only the uncommitted tail instead of from zero. The checkpoint is an optimization that may lag (a stale checkpoint redelivers a few already-processed messages, never loses one) and the recovered offset is clamped to the durable log head. Tested across reopen for resume-from-committed, idle-after-full-consume, stale-checkpoint redelivers-the-tail, and a StdFs-backed real-directory run.
- `ironbus-storage::checkpoint`: a crash-safe `Checkpoint` for small durable state (the committed consumer cursor, later the resilience counters). Two CRC32C-protected slots are written alternately by sequence and fsynced; on recovery the higher-sequence slot whose CRC validates wins, so a slot torn by a crash mid-write is ignored and the prior value survives. The checkpoint can regress to an earlier durable value after a crash (safe at-least-once: some processed messages redeliver) but never advances to a torn or invented one. Tests cover round-trip, latest-wins, a torn newest slot falling back, both slots torn recovering nothing, and power loss before the sync keeping the prior value.
- `ironbus-server::engine`: the single-topic queue engine, the synchronous heart that wires the durable log to the consumer primitives. `Engine::produce` appends a message and fsyncs before returning; `poll` hands out the next deliverable message (within a `max_in_flight` sliding window above the committed cursor) under a fencing token; `ack` commits it and advances the cursor over the contiguous prefix. An unacked message past its visibility timeout is redelivered on a later poll (fencing the stale token), and a message over max-deliver is parked rather than looping. Synchronous and deterministic (the caller supplies monotonic time), so the whole produce/consume/recover loop is testable without a runtime; the durable consumer cursor is follow-up, so a restart currently redelivers from zero (safe at-least-once).
- `ironbus-proto::message`: codecs for the PUB and ACK frame bodies (the produce and acknowledge wire messages). PUB carries flags, a producer timestamp, a u16-length key and headers, then the payload as the remainder; ACK carries the op (ack/nack/term/progress), the offset, the lease generation (fencing token), and a nack delay. Decoding is bounds-checked and never panics on a malformed body (typed `BodyError`), little-endian and portable; proptest round-trips and a never-panics-on-arbitrary-bytes property.
- `ironbus-proto::frame`: the wire frame envelope. A frame is a little-endian `u32` length prefix over a one-byte type tag (the verb: Connect, Info, Ping/Pong, Pub, Sub/Unsub, Ack/Nack, Flow, Ok/Err) plus a type-specific body. `encode_frame` and the streaming `decode_frame` validate the length against a 16-MiB-plus cap BEFORE allocating (so a hostile prefix cannot force a large read), report how many bytes a frame consumed or still needs, and let an unknown type tag decode at the envelope level for forward compatibility. Proptest round-trips, truncation-is-incomplete, and unknown-tag framing.
- `ironbus-core::delivery`: the delivery policy (`DeliveryConfig`) and the ack vocabulary (`AckVerb`: ack, nack with an optional delay, progress, term). `disposition` dead-letters a message once it exceeds `max_deliver` (default 5) and otherwise delivers; an unlimited cap (0) is rejected without an explicit opt-in and never dead-letters. `nack_backoff` returns the escalating per-attempt retry delay, clamped to the schedule's last entry. Pure and IO-free; the durable DLQ move (append plus tombstone under one fsync, idempotent on recovery) is the server's job.
- `ironbus-core::lease`: the SQS-style lease lifecycle (`LeaseTable`). A claimed message is in-flight for a visibility timeout; only an ack carrying the matching generation token removes it, an expired lease is redelivered under a bumped generation (fencing the previous holder, so a late ack after redelivery is rejected: no double ack), and `progress` extends the deadline by one window but never past a hard cap from the attempt start. The delivery count rides each grant for the max-deliver / DLQ decision. Pure and IO-free (the caller supplies monotonic time from the clock seam); a restart empties the table so every in-flight message redelivers.
- `ironbus-core::cursor`: `AckCursor`, the work-group commit cursor that advances one shared committed offset correctly under out-of-order acks. It keeps the watermark below which everything is acked plus a compact run-length-encoded set of offsets acked ahead of it, advancing the watermark over the contiguous prefix as gaps fill, so parallel draining never skips an unacked message (at-least-once) nor serializes the group. Duplicate acks are ignored; `resume` rebuilds it from a recovered committed offset. Pure and IO-free, proptest-verified (any ack permutation fully commits; ranges stay sorted, disjoint, non-adjacent; committed is monotonic).
- Crash-injection gates for the storage log (issues #21, #55): a per-PR integration harness that power-cuts the log at every durability boundary and corrupts segments, then asserts recovery yields a consistent, monotonic prefix with no acknowledged record lost and bounded, valid loss. Covers power loss before fsync (at every op boundary, with and without rolling, plus a randomized proptest), a torn (truncated) tail, last-record and mid-log corruption, and arbitrary single-byte corruption (never panics; a valid prefix or a clean error).
- `ironbus-storage::log`: the read path. `Log::read_from(start, max)` reads records from a log offset forward, crossing sealed and active segments, and is bounded by a new durable flushed offset (`Log::flushed_offset`) so a reader never observes a record that is not yet on stable storage. `sync` (and a roll, which fsyncs the sealed segment) advances the flushed mark. An in-memory segment directory maps an offset to its segment by binary search; reading below the oldest retained offset returns `StorageError::OffsetOutOfRange`.
- `ironbus-storage::log`: segment rolling and multi-segment recovery. `LogConfig` sets a soft per-segment size cap (default 64 MiB); `append` seals the active segment and starts the next one, continuing the offset and sequence space, once it reaches the cap (an empty segment is never rolled, so an oversized record still gets written). The old segment is sealed before the new one is discoverable, so a crash mid-roll is recovered by rolling forward: `Log::open` now treats a sealed highest segment as create-the-next-segment rather than an error. A fatal mid-roll error freezes the writer (`StorageError::WriterFrozen`) instead of risking a corrupt resume.
- `ironbus-storage::log`: the single durable, ordered `Log` (write path over one active segment). `Log::open` recovers the active segment, truncating any torn or unsynced tail to the last intact record, or creates a fresh segment 0 stamped from the clock seam and dir-synced; `append` assigns each record its monotonic offset and sequence and writes it; `sync` makes records durable. Reopening after a simulated power loss recovers exactly the synced prefix and reuses (never skips) the dropped record's offset and sequence. Segment rolling and the read path are follow-ups.
- `ironbus-storage::segment::SegmentWriter::resume`: reopen an already-validated segment at its recovered write head without rewriting the header (the recovery primitive `Log::open` uses).
- `ironbus-storage::naming`: segment file naming (`seg-<16-hex-digit-id>.log`, fixed width so lexicographic order equals segment-id order), a strict canonical parser that is the exact inverse of the name function (proptest round-trip both ways), and `segment_ids`, which enumerates a data directory in ascending segment-id order while skipping foreign files. The directory of self-describing files is the discovery authority, no manifest required.
- `ironbus-storage::fs`: a `Filesystem` seam (open, create-new, list, remove, exists, sync-dir) over one flat data directory of segment files, with an `InMemoryFs` that models directory-entry durability (a created-but-not-dir-synced file vanishes on power loss; a removal that was not dir-synced is undone) and a Unix `StdFs` that rejects names escaping the data directory. This is the substrate for the multi-segment log and recovery.
- `ironbus-storage::segment`: `SegmentWriter` (append records, sync, seal with footer) and `SegmentReader` (validate header, scan records, recover the valid prefix on a torn or corrupt tail), wiring the record and segment codecs to the `RandomAccessFile` seam. Tests cover round-trip, seal/scan, empty sealed segments, torn-tail recovery, power-loss (only synced records survive), and rejection of a footer bound to a different segment.

### Documentation
- Documented the cross-platform durability barrier and resolved #153: an acknowledged produce always clears a true device write-barrier. On Linux (the production musl target) that is `fdatasync`/`fsync`; on Apple targets `std` maps both `sync_data` and `sync_all` to `fcntl(fd, F_FULLFSYNC)` (a real drive-cache flush, not a plain `fsync`), which is exactly what `StdFile` relies on, so no redundant `fcntl` wrapper is added. Verified against the `std::sys::fs::unix` source. IronBus deliberately keeps `std`'s no-`ENOTSUP`-fallback behaviour: a filesystem that cannot honour the barrier freezes the writer and stops acking rather than silently downgrading durability. Added a platform durability table to the usage guide, a load-bearing comment on the sync path, and an Apple-gated test that exercises the `F_FULLFSYNC` path.
