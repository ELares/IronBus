### Added
- Official Go SDK for IronBus under `sdk/go/` (#1021, refs #761): a hand-written, dependency-light (`github.com/pierrec/lz4/v4` only) Go client that speaks the FROZEN wire protocol natively — no cgo, no generated stubs. It implements the full `[len:u32 LE][tag:u8][body]` envelope with the pre-alloc frame cap, the `Connect`/`Info` capability-bit AND negotiation, the 0xA7 auth section (`Bearer` / `Password`, both redacting via a `Credential` type that never prints its secret), the durable produce shapes (`Produce`, `ProduceWithAckLevel`, `ProduceFireAndForget`, `ProduceDedup`, `ProduceTo`, `ProduceSubject`), competing work-group consume with the full `(offset, generation)` lease discipline (`Subscribe`/`Fetch`/`Ack`/`Nack`/`Term`/`Progress`/`CumulativeAck`), named streams (`DeclareStream`/`QueryStream`/`BindSubject`), lz4-BLOCK decompression under the 8 MiB per-record cap, and the typed error surface (`*ServerError`, `*NotLeaderError`, `*InvalidAckLevelError`, `ErrClosed`). Correctness is pinned by 47 GOLDEN FRAME VECTORS exported byte-for-byte from the canonical Rust encoders by a new test-only exporter (`crates/ironbus-proto/tests/export_go_vectors.rs`, env-gated so it is a compile-only no-op in normal CI) into `sdk/go/internal/wire/testdata/golden_vectors.json`, where the Go conformance tests decode every vector and assert the decoded fields — so the Go decoder can never silently drift from the Rust wire. Ships five runnable, commented examples (`sdk/go/examples/{produce,consume_ack_group,streams,subjects_wildcard,cluster_notleader}`) mirroring the Rust example set (#1022) and a dedicated CI workflow (`.github/workflows/go-sdk.yml`: gofmt, `go vet`, `go test`, examples build). A UNKNOWN TAG stays terminal (never skipped) and a client whose reply round-trip times out mid-frame is discarded-and-redialed rather than reused — the wire's fail-closed contract carried faithfully into Go. Additive only: ZERO change to the broker or the wire.
- Runnable, heavily commented CLIENT EXAMPLES for both Rust client crates (#1022, refs #761): `crates/ironbus-client/examples/{produce,consume_ack_group,streams,subjects_wildcard}.rs` and `crates/ironbus-client-async/examples/{produce_async,consume_async}.rs`, mirroring the Go SDK's planned example set (#1021). Each is a complete program that runs against a live `ironbus serve` (`cargo run -p ironbus-client --example produce`; the broker address is the first CLI argument, else `IRONBUS_ADDR`, else `127.0.0.1:7777` — the CLI's flag > env > default precedence) and demonstrates the real public API: the three durable produce shapes (awaited `produce`, opt-in `produce_dedup`, the auto-pipelining `pipelined_producer` / async `produce_window`), competing work-group consume with the full `(offset, generation)` lease discipline (ack / nack-with-delay / advisories), named streams (declare / info / publish-to / subscribe-to and cross-stream isolation), and subject routing with wildcards (below). Examples are lint-gated like every source (`clippy --all-targets` covers them) and each was verified end-to-end against a live broker.
- `Client::bind_subject` / `Client::publish_subject` / `Client::subscribe_subject` (#585 client surface, refs #1022): the synchronous client now speaks the subject-addressed wire verbs the broker has served since M2-I9 (`BindSubject` tag 34, `PubSubject` tag 35, `SubSubject` tag 36) but no Rust client exposed. `bind_subject(stream, pattern)` binds a #567 pattern (`*` matches one token, `>` one-or-more trailing tokens, final position only) to a named stream — declare-on-bind, idempotent, `admin`-scoped on an auth-enabled broker. `publish_subject(subject, body)` publishes on a LITERAL subject, resolved fail-closed single-home: an unbound subject is the typed `NoStreamForSubject` reject (never a NATS-style silent drop) and a multi-covered one `AmbiguousSubject`; at-least-once server-ack exactly like `publish_to`. `subscribe_subject(subject, group)` resolves a literal subject to its one covering stream and binds the connection's fetch/ack to that stream's competing work-group (a wildcard in the SUBSCRIBED subject is the typed `InvalidSubject` reject this phase; wildcards live on the bind side). All three ride the existing negotiated stream-addressing capability (`ClientConfig::understands_streams`) and reuse the frozen proto codecs verbatim — ZERO wire or broker change, additive client surface only. Proven by a real-server end-to-end test (bind a wildcard, publish two covered literals into one offset space, reject an unbound publish with the stable code, consume + ack via the subject-resolved group, reject a wildcard subscribe). The async twin inherits the shared types; its port is deliberately deferred with the rest of the named-stream parity work (#681).

### Changed
- `TCP_NODELAY` is now set on every broker-side and client-side data socket (#1028, refs #1023): the broker's accepted data-plane connections, the cluster peer links on BOTH ends (the raft metadata dialer and its accepted links, the follower fetch dialer and the leader-side accepted data-plane links, the cross-cluster serve accepts, and the geo-pull / leaf-push dialers), the health/metrics HTTP handler, and both client crates' connect paths (`ironbus-client`, and `ironbus-client-async` as its verbatim port). IronBus traffic is small-frame request-response (per-message acks, single-in-flight producers, fetch round-trips, raft heartbeats) — the exact pattern where Nagle + delayed-ACK stacks an RTT-scale stall onto every awaited round-trip on a real network; every serious broker (NATS, Kafka, Redis) disables Nagle on both ends. The setsockopt is BEST-EFFORT everywhere: a failure degrades latency only, never correctness, so it never kills an otherwise-healthy connection (the broker logs it at debug; the clients ignore it). ZERO wire/behavior change beyond the socket option; the option is pinned by getsockopt read-back tests in all three crates. On loopback (where Nagle is not the dominant term, per the #1023 L2 probe) the awaited window=1 ack RTT is flat within run noise (p50 medians ~170 us before vs ~175 us after over 8 interleaved runs each with an 88-184 us spread; p99 median 383 -> 360 us) and streamed-publish throughput is unchanged (~128k msg/s medians on both sides) — the win is on real networks, where a delayed ACK is tens of milliseconds.

### Added
- Cooperative rebalance on JOIN — learner back-fill, promote only once caught up, no stop-the-world (V2-C5-I2, #617): a NEW node joins a running cluster as a NON-VOTING LEARNER, back-fills the committed metadata log by replication (raft-rs feeds a learner the log exactly like a follower), and is AUTO-promoted to a voter ONLY once it is CAUGHT UP to the committed high-watermark — while the cluster keeps serving committed produces and reads uninterrupted (no availability dip, no quorum stall). Adding the learner does NOT change the quorum math: a learner is non-voting (`voter_count`/`min_isr` are unchanged) until promoted, and the promotion is a committed joint-consensus change (#677, overlapping old+new majorities). The promotion GATE is fail-closed, read in-plane off the metadata Raft core: the leader promotes a learner only when its durably-replicated frontier (raft-rs `Progress::matched`, the prefix the learner has acked) has reached the leader's committed index (`LearnerCatchup::is_caught_up`) — a learner whose catch-up cannot be PROVEN (not tracked, or behind the bar) is never promoted, the metadata-plane analogue of the #722 `own_frontier >= committed_hw` failover gate. `MetadataRaftGroup::open_as_learner` seeds the existing voters as the learner's `ConfState` (without itself a member) so it follows that quorum and learns its own learner→voter role by replication; the driver's periodic F3 path drives the caught-up promotion (single proposer = the metadata leader). New CLI: `--cluster-join-as-learner` (the joining node) and repeatable `--cluster-pending-learner <id>` (a voter pre-declaring a learner's address so it can replicate to it without restarting). SINGLE-NODE is byte-identical: nothing of this constructs off-cluster, and the produce/consume hot path is unchanged. Proven by a real multi-node `#[cfg(unix)]` integration test (a 4th node joins a 3-voter cluster, is added non-voting with the voter count held at 3, the cluster keeps committing throughout, and it is promoted to a 4th voter only once `matched >= committed`) plus a fail-closed safety test (a never-started learner is never promoted and the quorum is unchanged) and unit tests for the gate predicate. DEFERRED to follow-ons: throttled / rate-limited re-replication of moved data (#619) and multi-partition routing (#693); snapshot-based catch-up pairs with metadata-log compaction (not yet implemented) — today the full committed log is replicated to the learner.
- Leader-completeness election restriction (the cluster-safety capstone, V2-C4-I4/I5, #614/#615): a partition leader candidate must hold the COMPLETE committed log up to the cluster-known high-watermark, so a stale or corrupt replica is INELIGIBLE to lead — by construction. `cluster::eligibility` (`ironbus-server`) defines eligibility as `(in the ISR, #691) AND (durable prefix >= the committed quorum HW, #691) AND (no detected divergence, #697)`, reusing the leader epoch (#668); the pure predicate `LeaderEligibility` and the leader-completeness inputs live IO-free in `ironbus-core::cluster_invariants`. The metadata-plane placement consults `eligible_leaders` and may designate a leader only from the eligible set, so the placement can never pick a stale/corrupt node — the construction that prevents the Jepsen NATS 2.12.1 failure (a corrupt node "managed to become the leader … despite its corrupt state", then deleted the stream, losing ~49.7% of acked writes). The placement/rebalance itself (WHICH eligible replica, and when) is C5 (#616+); this ships the eligibility function it consults plus the testable layer. Alongside it, the cluster recovery contract CI1–CI4 is ratified as `docs/CLUSTER_INVARIANTS.md` plus pure-function checkers in `ironbus-core::cluster_invariants` that mirror the single-node resilience checkers (`ironbus-storage`'s I1–I4): CI1 (in-sync replicas share the committed prefix), CI2 (a `C2-fsync` ack implies a quorum fsync, #691), CI3 (divergence is bounded + reported + repaired, never silently served or deleted, #697), CI4 (epochs monotonic, no stale-leader-commit, #668 + #614) — each a falsifiable pure function with a known-bad negative fixture (a sub-quorum ack, a silently-served / deleted divergence, an epoch regression, a committed-prefix mismatch). Single-node is byte-identical: the lone replica is its own ISR, is complete to its own HW, and cannot diverge from itself, so it is trivially eligible; the eligibility / CI layer never constructs in a standalone broker. `ironbus-core` stays IO-free, no on-disk format change, the metadata Raft election is unchanged (this constrains PARTITION leadership eligibility, layered on the placement).

### Added
- `Client::pipelined_producer()` / `pipelined_producer_with_window(window)` (#508): an auto-pipelining DURABLE single-producer handle, the client-side complement to the server group-commit gather (#454/#472/#507). It buffers a window of at-least-once publishes (default `DEFAULT_PIPELINE_WINDOW` = 64), serializing each into an owned wire frame so the caller's input buffers are free immediately, then writes the window as ONE pipelined batch (the `produce_window` wire discipline) so the broker collapses it under a single fdatasync. The caller drains acks at `flush()`/`finish()` (a `FlushSummary` tally). This LIFTS a single producer's durable throughput from ~one-publish-per-fsync to the group-commit rate (a measured isolated-disk `bench --mode publish` rose from ~240 msg/s to ~13.5k msg/s, ~55x, with per-op fsync cost dropping ~4004 us to ~63 us) while keeping the ack-implies-durable guarantee intact (every ack still means fsynced-durable; only WHEN the ack is observed moves). `bench --mode publish` gains `--autopipe` (sized by `--pubwindow`, default window when omitted) to drive it, with an additive `"auto_pipeline"` JSON field (schema version unchanged); publish-only, mutually exclusive with `--stream` and `--fire-and-forget`. ADDITIVE and NON-BREAKING: `Client::produce`'s fully-synchronous, one-publish-in-flight, durable-on-return contract is UNCHANGED. No broker or wire-protocol changes.

### Fixed
- `bench --mode subscribe` no longer HANGS when the broker retains fewer records than the preload count (#19 corpus work). The drain loop's count-bound stop required `recorded >= expected`, so if any preloaded record was shed under a byte cap (memory mode, or a disk drop policy) the drain looped forever waiting for records that would never arrive. It now also terminates once the queue has stayed empty for a grace window (the producer finishes before the drain starts, so a sustained-empty queue cannot refill), and reports how many records were shed. The termination predicate is extracted as a pure, unit-tested `drain_should_stop`.

### Changed
- `bench --mode subscribe` pre-loads via a pipelined produce window instead of a serial per-message produce (#19 corpus work). SUBSCRIBE measures the drain rate, so the preload's write speed is irrelevant to the metric; the old serial fdatasync-per-message preload made a large preload fsync-bound (minutes for no measurement value). The preload is now group-committed in chunks; each record still carries its sequence stamp.
- The `ironbus-bench` comparison rig gains a `Memory` (`memory`) durability label (#19/#114): the honest ephemeral, NOT-power-loss-safe label for IronBus `--storage memory`, a NATS JetStream memory-storage stream, and Redis with the AOF disabled, so the in-RAM throughput ceilings compare apples-to-apples and are never confused with a durable number.

HONEST result (RPi4 armv7, median-of-3, client SEND rate -- upper bound, not broker-accept): NATS core, a pure router that logs/offsets/compresses/persists nothing, leads the raw at-most-once send rate ~2-4x; IronBus QoS-0 is a durable log with acks turned off (consistent with it still assigning an offset, appending with a CRC, and lz4-compressing each message), and its DISK variant does at-most-once delivery that STILL durably appends -- which NATS core cannot do at all.

### Changed
- SIGHUP is now the runtime config-RELOAD trigger instead of a second stop signal (#380). `serve`'s signal handling moved from `ctrlc` to `signal-hook` so the signals are told apart: SIGINT/SIGTERM still perform the graceful stop (flush every committed cursor, exit 0, #195), while SIGHUP (or `systemctl reload`) re-reads the `--config` file and applies the LIVE-reloadable subset — the consumer-safe retention bounds (`max_retained_bytes` / `max_age_ms` / `max_messages`) and the disk-full policy — to the running engine WITHOUT dropping connections, then reports the outcome on stderr. The live apply runs on the append actor (`EngineHandle::with`), so it serializes with produces/acks under the engine's single owner with no lock and no hot-path cost, and it runs an immediate retention reap (still floored at the consumer protect offset, so a tightened bound never reaps below a live group's cursor). A cold-key change (segment size, data dir) is rejected and the running config kept; a change to a RESTART-REQUIRED key (durability, flush, the per-consumer credits, max-in-flight, max-connections, max-deliver, the total cap) is reported as NOT applied live and takes effect only on a restart; with no `--config` set, SIGHUP is a logged no-op. SIGHUP no longer stops the broker, so the previous `kill -HUP` footgun under the packaged unit's `Restart=on-failure` (a clean stop staying down) is gone, and the unit gains `ExecReload=/bin/kill -HUP $MAINPID`. The dependency swap drops `ctrlc` (and its transitive `nix`) and adds `signal-hook` + `signal-hook-registry` (both pure Rust, MIT OR Apache-2.0, on the deny.toml allow-list, C-FFI-free). The MUTATING wire `CONFIG SET`/`SAVE`/`DIFF` verbs remain deferred behind the #106 connection-scoped auth. Refs #195, #382, #431, #88.

### Added
- `Client::produce_stream(messages, window)` (#458): a FULL-DUPLEX sliding-window publish. The caller's thread keeps writing coalesced PUB batches while a scoped reader thread drains the FIFO acks concurrently from a cloned read half, with at most `window` produces un-acked; termination rides the wire's frame-order guarantee (a trailing Ping whose Pong proves the drain is complete). Reply semantics follow `produce_window` except that server Err replies are COUNTED in the returned summary (first one kept verbatim) instead of failing the call, since the stream has fully drained by then and the tally is the product (a shed under `drop-new` no longer discards the run's counts); `fire_and_forget` is forced clear; on success the connection stays fully usable. `bench --mode publish` gains `--stream` (requires `--pubwindow >= 2`) to drive it, with a `"stream"` field in the JSON object; per-produce fsync cost is not attributed in stream mode. No broker or wire-protocol changes.

### Changed
- `InMemoryFile::sync_data` now copies only the byte ranges written since the last sync into the durable image instead of cloning the whole file (#456). An in-memory group commit costs O(bytes appended) like a real fdatasync, not O(file): under `--storage memory` this removes a whole-segment memcpy per commit (82 percent of append-actor CPU in a profiled pipelined publish run) and a quadratic per-message copy at window 1. The durable image is byte-for-byte unchanged (unsynced-truncation tail retention, zero-fill growth, power-loss reverts all preserved; the determinism, crash-recovery, and power-loss suites pass unchanged).

### Changed
- The per-connection read chunk grew from a 4 KiB stack array to a 64 KiB zero-page heap buffer (#454). The pipelined produce window (#450) is pass-scoped, and a pass sees at most one read chunk, so 4 KiB silently capped the publisher pipeline at ~13 records per group commit on 256 B payloads (~40 fsyncs per 512-record window on the reference edge box). Untouched pages cost no resident memory, so idle connections are unaffected.

### Added
- `serve --commit-gather-us <us>` / `IRONBUS_COMMIT_GATHER_US` (#454): an opt-in bounded group-commit gather window. When a drain pass already holds at least two produces (evidence of a pipelining publisher; an unpipelined producer never pays the window), the append actor keeps collecting commands for up to the window before committing, so a pipelined publisher's whole in-flight window lands under one covering fsync instead of arrival-rate-sized slivers (measured on the reference edge box: a 512-record client window was committing as ~12 records per fsync). Default `0` keeps the actor byte-identical; acks keep their fsynced-durable meaning at any setting; validation caps the window at 1 second. The materialized-config line gains a `commit_gather_us=` field.

### Fixed
- An idle-evicted group's durable position now keeps pinning the retention protect floor as a GHOST until the group returns or an explicit unsub releases it (Closes #432).
  - Before, the sweep dropped the group's floor bookkeeping with its memory, so every segment sealed after the eviction was immediately reapable and a briefly-idle consumer could return to a one-time truncation; a restart already re-pinned the durable cursor as a live group, so runtime and restart semantics disagreed. The idle sweep now keeps the ghost, a returning group supersedes it with its live resumed cursor, and an explicit unsub (the consumer renouncing the position) releases it, so pinning is opt-out by unsubscribe, never implicit by absence.
  - The producer-only head fallback and the untouched-default-group rule (#424) are unchanged; the drop-oldest force-reap still ignores the floor, ghost or live. New engine tests pin all four behaviors; the CLI help and USAGE.md document the ghost rule.
- Docs now state everywhere that SIGHUP performs a graceful stop exactly like SIGTERM (flushes the committed cursors, exits 0) and that applying a config change is restart-only today: the validate-whole-then-swap re-read engine ships but runs only as a startup self-check, with the runtime trigger tracked in #380 (refs #88) (Closes #431).
  - Corrected the remaining overclaims that said the SIGHUP/re-read reload path is wired: three spots in `docs/CONTRACTS.md` (the config-models intro, the implementation-status Config note, and the #137-draft discrepancy entry), the `docs/CLI.md` env-mapping residual note, and the `config_reload` module doc comment in `crates/ironbus-cli/src/main.rs` (comment only, no behavior change). PR #429 had already corrected `docs/CONFIG.md` and `docs/EDGE_TUNING.md`.
  - Made the SIGHUP=stop behavior explicit where signal handling is described (`docs/CLI.md` `serve`, `docs/USAGE.md`, the README quick start) and added a "Signals and config changes" note to `docs/DISTRIBUTION.md`: under the packaged unit's `Restart=on-failure`, a clean stop is not restarted, so a `kill -HUP` sent expecting a reload leaves the broker down until it is started again; operators change config by editing the file and restarting.
- Made the installer's binary swap failure-safe and same-version re-runs a rollback-preserving no-op (Closes #421, Closes #422).
  - `install_binary` in `scripts/install.sh` now retains the rollback copy by COPY (`cp -p` to a sibling temp, then one atomic `mv` over `ironbus.prev`) instead of moving the live binary, and exactly ONE atomic `mv` changes the destination: a failed final swap leaves the existing binary untouched, and there is no longer a window where the destination does not exist for a supervised (`Restart=`) respawn to land in (mirrors the #348 rollback hardening).
  - A same-version re-run (the staged binary's SHA256 equals the live binary's, via the existing `sha256_of` plumbing) is now an idempotent no-op success that touches neither the destination nor `ironbus.prev`, so a config-management convergence run can no longer clobber the only rollback copy with bytes identical to the live binary.
  - New installer-harness tests: a same-version re-run preserves `.prev` and exits 0; the rollback copy survives an upgrade followed by a same-version re-run; a failed swap (read-only destination directory, and a rejected final rename) leaves the original binary present at the destination.
- Retention is no longer silently disabled for a deployment that only consumes through named groups (Closes #424).
  - The protect floor now skips a group that has never seen any consumer interaction or durable consumer state. The boot-created default group exists structurally, so before this fix its virgin offset-0 cursor pinned the floor forever in a named-groups-only deployment: every retention bound was a no-op, the log grew to `--max-total-bytes`, then drop-new shed every produce.
  - Any poll, ack, nack, term, progress, or subscribe on the default group marks it a real consumer with the unchanged slow-consumer protection; its durable cursor or attempts checkpoint restores the protection across restarts. With no touched group at all the floor is the durable head.
  - New engine tests pin all four behaviors (untouched does not pin, polled pins, untouched survives reopen, checkpointed resumes touched). `USAGE.md` (Bounding disk use) documents the rule, the restart nuance, and corrects the stale claim that no disk-full drop-oldest policy exists (`--disk-full-policy drop-oldest` shipped in #82).
- The systemd unit's three lifecycle helper lines (`ExecStartPre` consult/rollback, `ExecStartPost --ok`, `ExecStopPost --failed`) now run with the `+` full-privilege Exec prefix, while `ExecStart` stays fully sandboxed (Closes #420).
  - Unprefixed, `User=ironbus` + `ProtectSystem=strict` made every counter write next to the binary fail with EROFS: the failed `ExecStartPost` made systemd kill a healthy broker at the end of the grace window and restart it forever (`Restart=on-failure` with the rate limiter disabled), and the failed `ExecStopPost` meant the fall-back-after-N mechanism could never trigger. - The macro-bench coordinated-omission self-test is now a reliable, non-flaky CI gate (#284). It no longer `SIGSTOP`s the shipping broker (whose freeze did not reliably manifest on shared CI runners, an OS-scheduling artifact); instead it runs an in-process broker (the same `ironbus-server` engine + append actor + `serve`) over a `FaultFs` and freezes it deterministically by closing the `FaultFs` sync gate, which parks the group-commit `fdatasync` on a condvar. - The wire server now owns the engine behind a single append-actor thread instead of an `Arc<Mutex<Engine>>` held across the produce fsync (#177). Connection handlers fan in over a bounded `sync_channel` and send commands; the actor group-commits a drained batch of produces with ONE `fdatasync` and acks the whole batch only after it. This removes the head-of-line block (a stalled disk no longer freezes every connection) and amortizes the fsync. Pings are answered in the handler without touching the actor, so a stalled produce fsync cannot block another connection's ping (the explicit acceptance test, proved with a sync-gating fault fs). - The broker now persists the consumer cursor's acked-ahead set across a restart, not just the committed watermark (refs #60, #61): the engine checkpoint payload is now the full `AckCursor` snapshot (#235), so an out-of-order ack (one that leaves a lower offset unacked) survives a restart instead of redelivering. - Server-side escalating nack backoff (#63): when a nack carries no explicit delay, the broker now defers redelivery by the configured per-attempt backoff schedule (`DeliveryConfig.backoff_nanos`, indexed by the delivery attempt and clamped to the last entry) instead of redelivering immediately, so a flapping consumer backs off rather than hot-looping a retry. `ironbus serve` ships a default schedule of 100 ms, 500 ms, 2 s, 10 s, 30 s; an explicit `--delay-ms` (or wire delay) overrides it, and an empty schedule keeps the prior immediate behavior. `LeaseTable::deliveries` exposes the attempt count the engine indexes by. Tested at the lease and engine layers: the schedule defers redelivery and an explicit delay overrides it.
- `ironbus sub` disposition flags expose the full consumer ack vocabulary through the binary: `--nack [--delay-ms <n>]` requeues each fetched message for redelivery, and `--term` drops each without dead-lettering, alongside the existing `--ack`. At most one disposition applies to the batch (a second is a usage error, and `--delay-ms` requires `--nack`); with none, `sub` peeks and the messages stay in flight to redeliver after the visibility timeout. Each disposition prints its per-message result (requeued / dropped / committed / fenced).
- Golden-path acceptance slice (#133): an integration test that drives the real built `ironbus` binary end to end through the reachable part of the promised story, boot the broker, produce three messages (each ack carries the next durable offset), fan the batch out to a consumer that acks all three, restart the broker on the same data directory, then confirm the acked messages do not redeliver (the cursor was durable) and the log continues at the next offset. Gated to Unix (serve is Unix only in v1). The full #133 scenario (broadcast plus competing groups, overload spill, a simulated power cut, the loss report, the installer) is not built yet and stays open.
- `ironbus serve --checkpoint-interval <n>`: tune how many messages may be redelivered after an abrupt crash (the cursor-checkpoint interval), defaulting to 1024. A low value persists the consumer cursor more eagerly (at the cost of more checkpoint writes), which also makes restart-resume deterministic for the golden-path test.
- Term and progress over the wire (#63): the consumer ack vocabulary (ack, nack, term, progress) is now complete. `Term` is an intentional drop, the broker commits past the message so it never redelivers and is not dead-lettered (mechanically a commit, distinct from ack only in intent). `Progress` extends the lease by one visibility window so a consumer still working is not redelivered, reporting extended, cap reached (the lease is at its hard cap and will expire on schedule), or fenced. `ironbus-server` adds `Engine::term` and `Engine::progress` (plus `ProgressResult`), the session wires both ops to a one-byte status reply, and `ironbus-client` adds `Client::term` (returns dropped vs fenced) and `Client::progress` (returns a `ProgressOutcome`). Tested at the engine layer (term drops without redelivery, progress extends then caps at the hard cap under a controlled clock, stale-token fencing) and with a client round trip. The crash-atomic dead-letter-queue move and the server-side backoff schedule remain follow-ups under #63.
- Nack over the wire (#63): a consumer can negatively acknowledge a delivered message to request redelivery, immediately or after a delay. `ironbus-core` adds `LeaseTable::nack`, which requeues the lease at `now + delay` and fences the nacking token with a fresh generation, so a later ack of the same token cannot commit an unprocessed message (a real at-least-once protection), while keeping the delivery count so the next claim escalates it for `MaxDeliver`. `ironbus-server` adds `Engine::nack` (converts the wire delay in milliseconds to monotonic nanoseconds, and leaves the `MaxDeliver` / dead-letter decision to the existing poll path, so a message nacked past its cap is parked, not looped). The session wires the `Nack` op to a one-byte status reply (1 requeued, 0 fenced, same convention as ack), and `ironbus-client` adds `Client::nack(offset, generation, delay_ms)`. Tested at the lease, engine, and client layers, including the fence-then-redeliver path, the escalated delivery count, and a stale-nack no-op. The `Term` and `Progress` ops and a CLI nack surface remain follow-ups.
- The broker now persists the durable consumer cursor on the online path (#182). The engine checkpoints the committed offset once it advances at least `checkpoint_interval` offsets (`EngineConfig.checkpoint_interval`, default 1024 in `ironbus serve`), and the server also flushes it on a clean disconnect, so a restart resumes past acked messages instead of redelivering the whole log. This bounds crash redelivery to roughly `checkpoint_interval` while keeping the checkpoint write rate far below one per ack (edge flash endurance). The checkpoint stays a lagging optimization: a write failure costs redelivery on restart, never correctness, so it never fails an ack or a connection, and a forced checkpoint with no advance is a no-op. Verified by an engine bounded-replay test, a server clean-disconnect checkpoint test (the force-on-close path), and a real on-disk `ironbus serve` restart that resumes via the stored cursor.
- CI cross-compiles a static `ironbus` musl binary for the three edge triples (`x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl`, `armv7-unknown-linux-musleabihf`) on every PR with `cross`, asserts each is statically linked (no dynamic interpreter), and uploads each as a build artifact. This is the build half of the single-static-binary distribution story (#17); signing, SBOM, and the installer are follow-ups.
- `ironbus-cli`: the `ironbus` command-line binary, the first three verbs of the frozen command map (#136). `serve` runs an on-disk broker (creates the data dir, opens the durable engine on `StdFs`, binds loopback by default, serves until the process is signalled; Unix only in v1 with a clear error elsewhere, since on-disk storage is Unix-only). `pub` connects, appends one message (payload from an argument or stdin), and prints the durable offset. `sub` fetches up to a credit, prints one line per message, and with `--ack` acknowledges each (committed or fenced). Typed `CliError` mapped to the frozen exit-code scheme (#91): 0 clean, 1 usage, 5 broker unreachable, 70 internal. Hand-rolled argument parsing (no new dependency) for this small surface. Tested with a pub/sub/ack round-trip over an in-process broker and over a real on-disk broker, the usage-error paths, and the broker-unreachable exit code; smoke-tested as the built binary end to end. The versioned `--json` contract and the rest of the command tree (bench, info, consumer, peek, dump, and the offline forensics) are follow-ups under #91 and #136.
- `ironbus-client`: a synchronous client library. `Client::connect` handshakes with a broker over TCP, then `produce` (returns the assigned offset), `fetch` (returns the delivered messages, each with the offset and fencing generation), `ack` (returns whether it committed or was fenced), and `ping`. It frames the byte stream with a persistent buffer (so a read delivering several frames is never lost) and maps a server `Err` frame to a typed `ClientError`. Connect, read, and write timeouts (`ClientConfig`, finite defaults) bound every blocking call, so a silent or slow broker fails the call instead of wedging the caller forever. The client distrusts the peer's framing: it rejects an unknown frame tag (`ClientError::UnknownFrameType`), a wrong-shape `Ok` (a non-one-byte ack status or non-eight-byte produce offset, `ClientError::BadResponse`), and more deliveries than the requested credit. Tested with a real produce/fetch/ack round-trip and multi-message fetch against an in-process server, plus hostile-server cases (server `Err`, fenced ack, eight-byte-`Ok` ack confusion, over-credit fetch, unknown tag) against a scripted raw socket.
- Consumer fetch path: a client can now receive and acknowledge messages, completing the produce/consume loop over TCP. `ironbus-proto` adds a `Deliver` frame type and a `DeliverBody` codec (offset + lease generation + the message); `ironbus-server`'s session handles a `Flow` (fetch) request by polling up to the requested credit and streaming each message as a `Deliver` frame, terminated by an `Ok` carrying the delivered count, then the client acks each by its fencing token. `Engine::poll_now` polls using the engine's own clock. Tested end to end, including a full produce -> fetch -> ack round-trip over a real TCP socket.
- `ironbus-server::clock::SystemClock`: the production `Clock` over the OS clock (wall from `SystemTime`, monotonic from `Instant`), the real implementation of the seam `ironbus-core` cannot provide while staying IO-free.
- `ironbus-server::server`: a blocking, thread-per-connection TCP server. `serve` accepts connections until a shutdown flag is set, bounded by a connection cap (so a flood cannot spawn unbounded threads), and drives a `Session` per connection against the engine shared behind a `Mutex` (the single logical writer the storage layer requires; group-commit behind an append actor is a throughput follow-up). Integration-tested over real localhost sockets: a CONNECT+PUB round-trip appends to the engine and returns the assigned offset, and a malformed frame closes the connection.
- `ironbus-server::session`: the connection session that frames the wire protocol onto the engine. `Session::process` consumes the complete frames at the front of an input buffer (leaving a partial trailing frame for the next read) and writes response frames, dispatching the request/response verbs: Connect -> Info, Ping -> Pong, Pub -> Ok (with the assigned offset) into the engine, and Ack -> Ok (committing a delivered message via its fencing token). Pub/Ack before Connect, malformed bodies, and unsupported verbs reply Err without closing; a malformed frame envelope ends the session (a length-prefixed stream cannot resync). Synchronous and buffer-driven, so the async TCP server can drive it without owning IO.
- `ironbus-server::engine`: a durable consumer cursor. The engine now keeps the committed offset in a crash-safe `Checkpoint` (`cursor.ckpt` in the data directory); `checkpoint_cursor` records it, and `Engine::open` recovers it and resumes, so a restart redelivers only the uncommitted tail instead of from zero. The checkpoint is an optimization that may lag (a stale checkpoint redelivers a few already-processed messages, never loses one) and the recovered offset is clamped to the durable log head. Tested across reopen for resume-from-committed, idle-after-full-consume, stale-checkpoint redelivers-the-tail, and a StdFs-backed real-directory run.
- `ironbus-storage::checkpoint`: a crash-safe `Checkpoint` for small durable state (the committed consumer cursor, later the resilience counters). Two CRC32C-protected slots are written alternately by sequence and fsynced; on recovery the higher-sequence slot whose CRC validates wins, so a slot torn by a crash mid-write is ignored and the prior value survives. The checkpoint can regress to an earlier durable value after a crash (safe at-least-once: some processed messages redeliver) but never advances to a torn or invented one. Tests cover round-trip, latest-wins, a torn newest slot falling back, both slots torn recovering nothing, and power loss before the sync keeping the prior value.
- `ironbus-server::engine`: the single-topic queue engine, the synchronous heart that wires the durable log to the consumer primitives. `Engine::produce` appends a message and fsyncs before returning; `poll` hands out the next deliverable message (within a `max_in_flight` sliding window above the committed cursor) under a fencing token; `ack` commits it and advances the cursor over the contiguous prefix. An unacked message past its visibility timeout is redelivered on a later poll (fencing the stale token), and a message over max-deliver is parked rather than looping. Synchronous and deterministic (the caller supplies monotonic time), so the whole produce/consume/recover loop is testable without a runtime; the durable consumer cursor is follow-up, so a restart currently redelivers from zero (safe at-least-once).
- `ironbus-proto::message`: codecs for the PUB and ACK frame bodies (the produce and acknowledge wire messages). PUB carries flags, a producer timestamp, a u16-length key and headers, then the payload as the remainder; ACK carries the op (ack/nack/term/progress), the offset, the lease generation (fencing token), and a nack delay. Decoding is bounds-checked and never panics on a malformed body (typed `BodyError`), little-endian and portable; proptest round-trips and a never-panics-on-arbitrary-bytes property.
- `ironbus-proto::frame`: the wire frame envelope. A frame is a little-endian `u32` length prefix over a one-byte type tag (the verb: Connect, Info, Ping/Pong, Pub, Sub/Unsub, Ack/Nack, Flow, Ok/Err) plus a type-specific body. `encode_frame` and the streaming `decode_frame` validate the length against a 16-MiB-plus cap BEFORE allocating (so a hostile prefix cannot force a large read), report how many bytes a frame consumed or still needs, and let an unknown type tag decode at the envelope level for forward compatibility. Proptest round-trips, truncation-is-incomplete, and unknown-tag framing.
- `ironbus-core::delivery`: the delivery policy (`DeliveryConfig`) and the ack vocabulary (`AckVerb`: ack, nack with an optional delay, progress, term). `disposition` dead-letters a message once it exceeds `max_deliver` (default 5) and otherwise delivers; an unlimited cap (0) is rejected without an explicit opt-in and never dead-letters. `nack_backoff` returns the escalating per-attempt retry delay, clamped to the schedule's last entry. Pure and IO-free; the durable DLQ move (append plus tombstone under one fsync, idempotent on recovery) is the server's job.
- `ironbus-core::lease`: the SQS-style lease lifecycle (`LeaseTable`). A claimed message is in-flight for a visibility timeout; only an ack carrying the matching generation token removes it, an expired lease is redelivered under a bumped generation (fencing the previous holder, so a late ack after redelivery is rejected: no double ack), and `progress` extends the deadline by one window but never past a hard cap from the attempt start. The delivery count rides each grant for the max-deliver / DLQ decision. Pure and IO-free (the caller supplies monotonic time from the clock seam); a restart empties the table so every in-flight message redelivers.
- `ironbus-core::cursor`: `AckCursor`, the work-group commit cursor that advances one shared committed offset correctly under out-of-order acks. It keeps the watermark below which everything is acked plus a compact run-length-encoded set of offsets acked ahead of it, advancing the watermark over the contiguous prefix as gaps fill, so parallel draining never skips an unacked message (at-least-once) nor serializes the group. Duplicate acks are ignored; `resume` rebuilds it from a recovered committed offset. Pure and IO-free, proptest-verified (any ack permutation fully commits; ranges stay sorted, disjoint, non-adjacent; committed is monotonic).
- Crash-injection gates for the storage log (issues #21, #55): a per-PR integration harness that power-cuts the log at every durability boundary and corrupts segments, then asserts recovery yields a consistent, monotonic prefix with no acknowledged record lost and bounded, valid loss. Covers power loss before fsync (at every op boundary, with and without rolling, plus a randomized proptest), a torn (truncated) tail, last-record and mid-log corruption, and arbitrary single-byte corruption (never panics; a valid prefix or a clean error).
- `ironbus-storage::log`: the read path. `Log::read_from(start, max)` reads records from a log offset forward, crossing sealed and active segments, and is bounded by a new durable flushed offset (`Log::flushed_offset`) so a reader never observes a record that is not yet on stable storage. `sync` (and a roll, which fsyncs the sealed segment) advances the flushed mark. An in-memory segment directory maps an offset to its segment by binary search; reading below the oldest retained offset returns `StorageError::OffsetOutOfRange`.
- `ironbus-storage::log`: segment rolling and multi-segment recovery. `LogConfig` sets a soft per-segment size cap (default 64 MiB); `append` seals the active segment and starts the next one, continuing the offset and sequence space, once it reaches the cap (an empty segment is never rolled, so an oversized record still gets written). The old segment is sealed before the new one is discoverable, so a crash mid-roll is recovered by rolling forward: `Log::open` now treats a sealed highest segment as create-the-next-segment rather than an error. A fatal mid-roll error freezes the writer (`StorageError::WriterFrozen`) instead of risking a corrupt resume.
- `ironbus-storage::log`: the single durable, ordered `Log` (write path over one active segment). `Log::open` recovers the active segment, truncating any torn or unsynced tail to the last intact record, or creates a fresh segment 0 stamped from the clock seam and dir-synced; `append` assigns each record its monotonic offset and sequence and writes it; `sync` makes records durable. Reopening after a simulated power loss recovers exactly the synced prefix and reuses (never skips) the dropped record's offset and sequence. Segment rolling and the read path are follow-ups.
- `ironbus-storage::segment::SegmentWriter::resume`: reopen an already-validated segment at its recovered write head without rewriting the header (the recovery primitive `Log::open` uses).
- `ironbus-storage::naming`: segment file naming (`seg-<16-hex-digit-id>.log`, fixed width so lexicographic order equals segment-id order), a strict canonical parser that is the exact inverse of the name function (proptest round-trip both ways), and `segment_ids`, which enumerates a data directory in ascending segment-id order while skipping foreign files. The directory of self-describing files is the discovery authority, no manifest required.
- `ironbus-storage::fs`: a `Filesystem` seam (open, create-new, list, remove, exists, sync-dir) over one flat data directory of segment files, with an `InMemoryFs` that models directory-entry durability (a created-but-not-dir-synced file vanishes on power loss; a removal that was not dir-synced is undone) and a Unix `StdFs` that rejects names escaping the data directory. This is the substrate for the multi-segment log and recovery.
- `ironbus-storage::segment`: `SegmentWriter` (append records, sync, seal with footer) and `SegmentReader` (validate header, scan records, recover the valid prefix on a torn or corrupt tail), wiring the record and segment codecs to the `RandomAccessFile` seam. Tests cover round-trip, seal/scan, empty sealed segments, torn-tail recovery, power-loss (only synced records survive), and rejection of a footer bound to a different segment.

- Documented the cross-platform durability barrier and resolved #153: an acknowledged produce always clears a true device write-barrier. On Linux (the production musl target) that is `fdatasync`/`fsync`; on Apple targets `std` maps both `sync_data` and `sync_all` to `fcntl(fd, F_FULLFSYNC)` (a real drive-cache flush, not a plain `fsync`), which is exactly what `StdFile` relies on, so no redundant `fcntl` wrapper is added. Verified against the `std::sys::fs::unix` source. IronBus deliberately keeps `std`'s no-`ENOTSUP`-fallback behaviour: a filesystem that cannot honour the barrier freezes the writer and stops acking rather than silently downgrading durability.
